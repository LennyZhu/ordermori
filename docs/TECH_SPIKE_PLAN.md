## 1. 优先级、入口条件与停止边界

| 顺序 | Spike | 目的 | 当前状态 |
| --- | --- | --- | --- |
| 1 / 最高 | PNG 渲染可靠性 | 决定能完整、清晰、稳定输出的渲染方式 | Not Executed |
| 2 | iOS Share Sheet 与二维码 | 确认真实发送 / 保存后的清晰度、扫码与取消反馈 | Not Executed |
| 3 | SQLite 与备份 | 证明原子创建、持久化、安全恢复及额度不回退 | Not Executed |

执行任何 Spike 都需要下一阶段单独授权。优先级不授权立刻建工程；第 4 项交易实验可安排在核心开单与 PNG 方案确认后，不阻塞前期 UI 和订单逻辑的技术设计。

在获准实验前先做一次版本预检：SDK 58 / RN 0.88 为优先候选，SDK 57 为兼容性回退候选；expo-iap 维护者的已验证基线仍为 SDK 57 / RN 0.86，与 SDK 58 存在待验证差异。**SDK 尚未冻结，本项目尚未安装依赖或完成原生构建，官方版本文档不构成本项目兼容性 PASS。** 实际构建前须核对精确发布包、原生版本、peer dependencies 和 Node.js / Xcode / iOS 工具链，统一使用一个 SDK 矩阵；不能混用 57 / 58 的依赖矩阵，也不能把后续降级后的结果沿用为原基线通过。

## 2. 共用样例、环境与证据

### 2.1 样例与产品边界

- 客户全部为虚构标识，不使用真实客户姓名、电话、地址、订单或银行流水。
- 两款模板：黑白极简、韩系柔和，均为 Free；Free 图底部有 Made with OrderMori，Pro 可去标并选允许的预设强调色。
- 订单长度：短单（1 项）、10 项、20 项；最长商品名 120 字符，备注 500 字符。English、繁體中文及混排都覆盖；字符计数口径和边界最终值仍待产品确认，不借实验静默更改。
- 收款 A 官方码 + 同方式文字、B 只有官方码、C 只有文字、D 无可用资料；D 只能非正式预览，不能伪造完整付款通知。FPS / PayMe / 银行资料按 PRD，可能固定金额的码需商家核对。
- 排版实验可用明确非付款占位素材；扫码通过必须换成用户授权的官方测试二维码，不能自造 PayMe / FPS 码冒充。真实测试收款图及解码内容不提交公开 Git 仓库。
- 费用使用整数分；包含 PRD 的自訂配送 HK$230.00 / 顺丰运费到付 HK$200.00 对照、0 总额与超限拒绝案例。

### 2.2 环境与证据要求

未来记录 SDK、RN、React、候选包精确版本 / tag、原生依赖、构建模式、设备型号、系统版本、可用空间、语言、字体与资源尺寸。至少在计划最低配置的真实 iPhone 和一台较新真实 iPhone 检查关键路径；具体设备、最低系统与 iPad 是否纳入首发仍待确认。

原生库使用 Development Build；性能比较关闭远程 JS 调试并说明是开发、性能或发布构建，不能拿 Expo Go / 模拟器表现替代正式设备证据。性能数字使用同一构建和同一组样例；允许未来 Xcode Instruments / 内存工具采集，不在本轮运行。

每次实验结果至少包含：样例 ID、操作、预期、实际、时长、峰值内存 / 图片尺寸等适用指标、脱敏截图或文件哈希、失败恢复结果、结论和待办。只完成本地 StoreKit 测试就写本地结果，不能写已通过 Apple Sandbox 或真实地区价格验证。

## 3. Spike 1 — PNG 渲染可靠性

### 3.1 目标、最小范围与依赖

P：纵向单张 PNG、两款模板、长内容完整、官方码完整、预览一致。A：view-shot 可捕获独立视图 / ScrollView，Skia v2 有绘制快照能力。R：优先分阶段验证独立 RN 付款通知视图 + view-shot 6.1.1；Skia 2.14.0 仅为达到触发条件后才启动的对照候选，不作为第一阶段必须同时实现的第二套完整渲染器。H：两者在实际 SDK 组合下的高度、字体、像素与内存表现均未知。

最小范围仅为合成订单输出，不做完整首页、商品系统、数据库或 IAP；权益用明确的本地测试输入模拟，不伪称已购买。阶段 A / B 只需候选 Expo Development Build、view-shot、必要本地图片 / 字体、文件系统与测量工具；只有进入阶段 C 才增加 Skia 对照。**本轮均未安装或建立。**

版本资料：[view-shot 6.1.1](https://github.com/gre/react-native-view-shot/blob/v6.1.1/README.md)、[Expo Skia 推荐版本](https://docs.expo.dev/versions/latest/sdk/skia/)、[Skia v2 Canvas](https://wcandillon.github.io/react-native-skia/v2/docs/canvas/overview/)；适用版本与风险记录以 TECH_DESIGN 第 2、6 节为准。

### 3.2 验证方法

按以下阶段顺序推进，不要求并行实现两套渲染器：

| 阶段 | 最小验证范围 | 推进条件 |
| --- | --- | --- |
| A：view-shot 基本方案 | 先做黑白极简；短单作对照，代表性 20 项长单包含 120 字符商品名、500 字符备注、中英文混排、Logo 及官方码 | 确认完整高度、可读性、预览一致，并检查适用的二维码、安全、性能及失败恢复门槛后，基本方案可行才进入 B；不宣称整个 Spike 已通过 |
| B：view-shot 完整边界 | 补齐韩系柔和，完成两模板 × 三长度 × 三语言的 18 个基础样例及必要 A–D 收款边界 | 第 3.3 节全部门槛及第 3.4 节人工验收满足后，才可判定 view-shot 方案通过；通过后无需为对照再实现 Skia |
| C：条件触发的 Skia 对照 | 仅当 view-shot 在 A / B 经合理修复和复测后，仍无法满足高度、完整性、内存或稳定性等既有要求时启动 | 先记录失败样例、修复尝试与残留问题；Skia 先复现相同失败样例，若基本方案可行再补齐同等完整矩阵与全部验收门槛，不把少量样例成功当最终通过 |

合理修复包括布局 / 捕获范围、图片字体等待、像素换算及资源释放问题；须记录修复和复测证据，不能通过减商品数、截内容、缩小到难读或降低 PRD 要求来使候选勉强通过。

各阶段按其范围使用以下方法；完整矩阵及门槛始终保留：

1. 阶段 A 先建立黑白极简代表样例，阶段 B 再补齐 2 模板 × 3 长度 × 3 语言的 18 个基础样例，包含最长名称和备注；A / B / C 收款形态在样例间轮换并补齐覆盖，另检查 D 不正式输出。无需机械全排列全部维度，但每个必要边界必须有实际证据。
2. 为每项商品使用可识别的虚构编号，核对第 1、10、20 项、完整名称、备注、总额、收款区及底部说明均存在，无屏幕裁切。使用专用捕获根节点，不调用整屏截图；排除虚拟化列表漏项。
3. 等待文字、图片及字体就绪后取得完整内容高度。检查生成文件实际宽为 1080px 候选，高度随内容变化；在不同 PixelRatio 上记录尺寸，不假定 main README 的 sizeUnit 参数存在于 6.1.1。
4. 正式预览直接显示待输出的同一文件；检查原图及放大后的中文字形、混排、Logo、金额和二维码等比 / 留白，预览与文件哈希 / 来源一致。
5. 对当前阶段的 view-shot 样例记录冷启动、至少 20 次热生成的原始耗时与 p95；采集原生进程峰值内存，不只看 JS heap。观察连续 20 次生成与释放后的内存走势。仅在阶段 C 被触发后，用同样的失败 / 最坏样例与相同测量口径对照 Skia，不要求第一阶段同时测两套实现。
6. 注入图片未加载、文件丢失、生成异常、取消 / 返回及生成中订单版本或权益变化。失败不分享、不改订单和额度；重试不重复创建任务。记录可支持高度及失败边界，不以缩字截字掩盖。

### 3.3 通过与失败条件

| 检查 | 通过条件 | 失败处理 |
| --- | --- | --- |
| 完整性 | 18 个基础样例及必要 A–D 边界全部符合预期；无丢项、重叠、裁切、假码或缺尾部 | 修正布局 / 等待条件；候选无法完整覆盖时进入备选，不宣称通过 |
| 图像 | 实际宽 1080px 候选，动态高度；CJK 无缺字，金额准确，二维码比例与必要留白完整 | 比较像素换算、字体资源与重采样；不能只提高 DPI 标签 |
| 预览 | 正式预览与导出的同一文件一致；数据 / 权益变化让旧生成失效 | 固定输出数据版本并重新生成，不分享过期图 |
| 耗时目标（U） | 暂定短单热生成 p95 ≤ 1.5 秒，20 项最坏样例 p95 ≤ 5 秒；需按确认设备评审 | 记录各阶段耗时与构建模式，优化或换候选，不把暂定目标写成已测能力 |
| 内存目标（U） | 暂定峰值增量 ≤ 200 MiB；20 次释放后稳态增量 ≤ 20 MiB，无持续单调增长、OOM 或系统终止 | 分析位图副本 / GPU 回读 / 生命周期；阈值和设备须人工确认 |
| 失败恢复 | 所有故障案例均无有效分享文件、无半成品成功提示，输入可保留、可重试 | 不通过该故障项，修复后仅重跑受影响矩阵 |

阶段 A 可行只允许推进完整边界验证，不能代替上表或人工验收。view-shot 经合理修复及复测仍不达要求时，按第 3.2 节触发 Skia 对照；Skia 不通过也不能理论宣布可用。分块绘制 / 流式编码为单张 PNG 是进一步备选，须证明最终没有重新整图分配。两者都不达标则提交证据供用户评审技术或产品边界，不自动减商品数量、缩二维码、改多张图或 PDF，不降低 PRD 要求。

### 3.4 人工与交付证据

需要用户 / 指定测试者在真实设备上检查阅读、放大、模板观感与字体；开发者未来采集尺寸、内存和时间。输出阶段结果、失败样例、修复记录与受支持边界；只有触发 Skia 时才补候选对照表。当前无图片、性能数据或通过结论。

## 4. Spike 2 — iOS Share Sheet 与二维码

### 4.1 目标、最小范围与依赖

P：系统分享、不指定联系人、不自动标记付款、官方码不改。A：expo-sharing 支持本地文件分享，SDK 58 MediaLibrary 有 Asset.create 新接口。H：WhatsApp 接收压缩、扫码、权限与 Files 保存结果必须真机验证。

最小范围为 Spike 1 合格本地 PNG 的分享 / 保存；不加入消息平台集成、自动联系人发送或真实付款。依赖 SDK 匹配的 expo-sharing、expo-media-library、文件系统、真实 iPhone、安装 WhatsApp 的接收设备，以及用户授权的官方测试收款码。[Sharing](https://docs.expo.dev/versions/latest/sdk/sharing/)、[MediaLibrary](https://docs.expo.dev/versions/latest/sdk/media-library/)。

### 4.2 验证方法

1. 对两模板的短单和最长合格单，选择 A / B 官方码场景，通过系统面板手动发送到用户控制的测试会话；另检查纯文字 C 与 D 禁正式输出。
2. 接收设备打开实际收到的图片，核对商品末行、费用、总额与说明；记录发送方式、是否原图 / 普通图片、接收宽高及压缩影响。
3. 测试者用对应官方支付工具扫码，仅核对识别与收款对象 / 固定金额适用性，不确认或执行付款，不将收款信息写入日志或公开资料。
4. 手动取消分享、关闭面板、选不可用路径及触发文件缺失；检查订单 / 额度完全不变。shareAsync 的 Promise<void> 不能证明取消、送达或已付款；若没有原生完成信息，采用中性面板反馈，不编造结果。
5. 分别测试保存到照片与“存储到文件”候选路线，核对实际文件可打开；照片权限拒绝 / 添加权限 / 有限访问、Files 提供者不可用 / 用户取消时保留数据并提示可行重试。
6. iPhone 竖屏、小屏及受支持 iPad 的面板锚点 / 安全区域要覆盖；iPad 是否支持待确认。保存入口最终选相册、Files 或两者仍待产品审核，实验只是给出证据。

### 4.3 通过、失败与备选

| 检查 | 通过条件 | 失败后的处理 |
| --- | --- | --- |
| 接收清晰 | 两模板长短样例接收后商品、总额、说明完整可读，真实末项存在 | 调整候选尺寸 / 输出，重测相同默认发送路径，不能只验证发送端 |
| 扫码 | 每种授权官方码的选定样例在接收设备连续 3 次可识别，商家确认对象正确；不执行付款 | 保留原图，检查缩放 / 留白 / 压缩；必要时评估文件发送路径并记录差异，不重编码支付码 |
| 状态边界 | 所有分享、保存、复制、取消 / 失败路径都不改付款或创建计数 | 修复业务边界；任何自动已付款即失败 |
| 权限 / 取消 | 不强迫全相册授权；拒绝、取消与错误无数据丢失或假成功；可选择其他已支持路径 | 明确权限和结果能力；若 UI 必须区分取消，评审原生完成回调，不宣称当前 API 已具备 |
| 文件生命周期 | 面板需要读取时文件仍存在，结束后临时资源可安全回收；长期原图不被重生成覆盖 | 调整引用租约 / 清理时机，禁止提前释放捕获文件 |

**必须人工完成** WhatsApp 目标选择、接收检查、官方工具扫码、照片 / Files 权限与真机体验；自动化未来只验证本地前置条件和状态不变。当前没有真实发送、扫码或权限测试结果。

## 5. Spike 3 — SQLite 与备份

### 5.1 目标、最小范围与依赖

P：金额快照、三维状态、首次创建原子计数、单草稿、整体恢复与可信较高额度。A：expo-sqlite 有独占事务和 backupDatabaseAsync，SQLite 有 Online Backup API。R：文件先就绪、受信活动 schema 内事务导入；H：实际 API 组合、故障恢复及归档安全还没有证据。

未来最小实验只用合成数据库与本地测试文件，不搭建完整 App，不接 IAP。依赖 SDK 匹配的 expo-sqlite、expo-file-system、expo-document-picker 及经过评审的 ZIP 候选；具体版本见 TECH_DESIGN。先验证数据库核心，再验证实际包含素材的备份，不把仅 DB 通过当作完整备份通过。检查导出容器及业务库没有 Apple 凭证、JWS 或隔离权益缓存；伪造备份 Pro 字段也不能解锁。[Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/)、[SQLite Backup API](https://www.sqlite.org/backup.html)。

### 5.2 验证方法与范围

1. 测试 TECH_DESIGN 第 7 节矩阵：9→10、拒绝第 11、相同 ID 重试、不同请求争末次额度、事务中每个关键写入点失败，核对 Order / Items / Ledger / 计数一起成功或回滚。
2. 保存单草稿后关闭并重开，确认已持久化输入、shop_id、买家为空草稿合法；复制只带商品初值、生成新 ID，不带状态 / 时间 / 旧收款；首次正式保存才校验买家并计数。
3. 改商品默认价、店铺 Logo / 收款码、语言后核对旧订单快照；付款误标纠正不解锁金额，退款不消除履约；跨店引用应被拒绝，即使 MVP 只有一家店。
4. 规划至少一个旧 schema 测试夹具到候选 schema 的迁移，验证副本预检查、版本拒绝和失败回滚；不执行备份自带 SQL、触发器或扩展。
5. 使用 Online Backup 对正在有受控写入的 SQLite 建快照，持有素材一致性租约，生成清单及实际文件归档；证明不是直接复制 live DB / 忽略 WAL。
6. 对合成 1000 张订单与 100 个素材的代表样本，以及约 100 MiB 的压力备份记录时间 / 空间；这些是实验样本，不是产品硬上限。比较原始 / 恢复后的业务字段与文件哈希，必要原 PNG 保持原貌。
7. 注入坏哈希、缺图、重复订单 ID、非法金额、非法状态、跨店资料、未来版本、恶意绝对路径 / .. / 符号链接、重复归档路径、解压膨胀及不可信计数字段，要求在替换活动数据前拒绝。
8. 在选文件、复制素材、事务导入各写入点和提交前后注入中断；模拟 ENOSPC / 锁冲突 / 写失败，不填满用户整部设备。重开后核对原数据或完整新数据、合法文件引用及正确累计计数，禁止半恢复。
9. 分别恢复可信 8 / 5→8、3 / 10→10、10 / 10→10；重复恢复不加计数，不按当前订单行数重算，编号分配高水位不回退；备份 Pro 标志不解锁。

### 5.3 通过、失败与备选

| 检查 | 通过条件 | 失败后的处理 |
| --- | --- | --- |
| 原子性与幂等 | 全部事务 / 并发 / 重试样例满足预期，无半单、重复编号、重复 Ledger 或多扣额度 | 调整服务事务、唯一约束与连接使用；不靠按钮防抖代替 |
| 持久化与快照 | 重开后输入和快照一致，默认价更新不回写，状态 / 金额锁不丢 | 修复写入和迁移，不用内存状态遮掩丢失 |
| 备份完整 | 订单、设置、商品、草稿、历史、额度与必要实际文件逐项一致 | 修复快照 / 清单协调，不降级为只备份 DB 或文件路径 |
| 恢复安全 | 全部不可信样例在活动数据被替换前拒绝；失败原数据及已记录计数不降低；重复恢复不重复计数 | 归档库不支持安全检查则更换或增加受审本地适配，不直接信任其 unzip |
| DB / 文件一致 | 每个故障点重开后无新 DB 指向半复制素材，旧资源未提前清理；完整成功才提示 | 调整素材先就绪与事务导入；若需要原生持久写入能力，先评审，不宣称跨资源天然原子 |
| 版本与空间 | 不支持版本明确拒绝；空间不足无原数据破坏；记录所需额外空间及可恢复状态 | 修订预算、清理策略及迁移边界；不得静默部分导入 |

备选可比较 SQLite 其他官方安全快照方式或本地原生文件适配，均须重新验证高水位与资源一致性。不能以覆盖 live DB 后补计数、自动清零或新增服务器绕过困难。

## 6. Spike 4 — StoreKit 一次性买断

### 6.1 目标、最小范围与依赖

P：Non-Consumable，一次买断且正常无期限，无订阅月费 / 年费；Pro 全局权益，不绑定店铺；价格为 Apple 实际地区价，HK$88 仅候选。A：StoreKit 2 有验证结果、当前权益及交易更新；OpenIAP 有相应本地接口，但维护者更推荐服务器验证。

R：先评估 expo-iap 的 StoreKit 2 设备端已验证交易与当前权益桥接；SDK 58 与其 SDK 57 验证基线的差异、无可信服务器验证下的客户端逻辑 / 缓存篡改风险均待审。不默认配置 IAPKit API Key，不默认接入 RevenueCat、其他托管购买验证服务、自建验证后端或其他商店。普通购买成功回调、本地 Pro 布尔值或未验证交易均不能作为有效购买证明。

所需条件是未来获准的原生 Development Build、Apple 开发工具及测试设备；测试产品标识需另行确认。先安排本地 StoreKit 配置实验，之后在另行授权且有相应配置时才做 Sandbox / 实际地区价格验证。**本轮不创建 .storekit 文件或 App Store Connect 商品。**

资料：[Apple VerificationResult](https://developer.apple.com/documentation/storekit/verificationresult)、[currentEntitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements)、[Xcode 本地 StoreKit 测试](https://developer.apple.com/documentation/xcode/setting-up-storekit-testing-in-xcode)、[OpenIAP Expo 基线](https://www.openiap.dev/docs/setup/expo)、[维护者验证取舍](https://www.openiap.dev/docs/features/validation)。

### 6.2 验证方法

1. 核对候选精确发布包的配置插件、默认配置及生成的原生配置 / 依赖，记录是否引入非预期网络、托管服务、API Key 要求或交易上传；不能因未填 Key 就假定没有服务依赖。再核对构建、本地验证、当前权益、交易监听 / 恢复、撤销字段的真实导出和语义；验证只处理预期产品、对应交易与环境。签名有效但已撤销的交易不能继续授予 Pro。必要语义不足须报告技术缺口并评估轻量原生 StoreKit 2 适配，不擅自接入第三方后端。
2. 本地 StoreKit 测试覆盖购买成功、用户取消、失败、待处理、重复交易事件与恢复；测试数据不等于生产 Apple 商店证据，不把本地设定的价格当真实地区价格。
3. 验证已确认 Pro 在离线 / 商店查询失败 / 未取得有效撤销结果时继续合理使用，不引入定时过期或周期续证；此前从未验证的未知状态不能用于首次解锁。
4. 模拟有效退款 / 撤销交易，确认不删订单、不改金额、商品、状态、历史、模板 / 强调色快照或独立原 PNG。合格未付款订单重新导出先提示，再带 Free 标记与模板默认色；已付款等仍禁新催款图。
5. 模拟 currentEntitlement 空结果、Apple 账户变化或查询异常，区分“已确认撤销”和“未知”；API 若不足以可靠区分，记录桥接缺口，不能擅自撤销或永久盲信。
6. 在未来 Sandbox 条件具备后，人工验证购买 / 恢复及至少两个可用地区的 Apple 本地化实际价格；地区条件不足时该项标 Blocked / Not Tested，不能用手工填价代替。恢复业务备份不改变购买权益，换店上下文也不重新购买。

### 6.3 通过、失败与备选

| 检查 | 通过条件 | 失败后的处理 |
| --- | --- | --- |
