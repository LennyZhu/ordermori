## 1. 产品定位

### 1.1 OrderMori 是什么

**OrderMori 是专为香港 IG Shop 和小型网店设计的轻量开单助手。** 核心价值是快速开单、分享清晰专业的付款通知，以及跟进订单的收款和发货进度。英文品牌理念：**Create. Share. Track.**

采用 iOS First、English + 繁體中文（香港）、Local-First、Offline-First、无需注册，尽量不依赖自建服务器。商家在手机上建立订单，通过系统分享交给客户，并自行登记付款和履约进度。

产品解决“小店在私讯中接单，商品、金额和收款说明零散，容易漏记或重复确认”的问题。首版以香港业务规则、HKD 单币种、PayMe 和 FPS 为主，保留未来全球上架的可能性，不承诺其他地区的支付支持、多币种或汇率换算，不扩展为复杂网店 SaaS。

### 1.2 目标用户与核心场景

| 用户 / 场景 | 核心需求 |
| --- | --- |
| 香港 IG 饰品店 | 把私讯中确认的商品、数量、金额快速整理成订单 |
| 手作及礼品卖家 | 发出美观易读的付款通知，手动跟进收款和发货 |
| 小型服装店 | 复用常见商品及默认价格，逐单确认费用和配送方式 |
| 通过 Instagram / WhatsApp 私讯接单的个人卖家 | 无需复杂店铺后台，也能保留清楚的本机经营记录 |

典型使用场景是“一人、一部手机、本机经营记录”。客户无需安装 App；首版没有商家账号注册、客户账号或客户地址簿系统。

### 1.3 商业目标

- 让商家愿意反复使用快速开单和分享流程，以清楚、美观、可靠的付款图片建立产品价值。
- Free 提供累计前 10 张真实订单的完整基础流程和两款模板，Pro 通过无限创建、移除品牌标记和品牌强调色形成一次性买断价值。
- 在扩大功能前，先验证商家是否能独立完成开单、是否愿意把图片发给客户，以及是否愿意购买 Pro。
- 易用性目标暂定为：完成基础店铺配置后，熟悉流程的商家可在约 60 秒内保存并准备分享一张包含 3 项商品的简单订单；测试时需说明输入内容和设备条件。这是待验证目标，不是已测结果。

### 1.4 项目独立性

OrderMori 与 HomeyPaw 完全独立，不共享产品代码、业务数据、账号体系、数据库、后端或商业化配置。不复制其业务设计；本 PRD 不产生对其他项目的修改要求。

商家无需先维护商品目录才能开单。首版只提供轻量商品复用，不建立独立复杂商品管理后台、SKU、库存或客户管理模块。购买及恢复购买需要网络和 Apple 平台服务，不属于离线承诺。

## 3. 明确不做事项

- 不做云同步、自动云备份、跨设备实时同步或账号登录体系。
- 不为免费额度防绕过新增设备指纹、云端额度服务器或复杂反作弊系统。
- 不做多人协作、员工权限、团队共享或网页管理后台。
- 不做复杂库存、采购、商品规格管理或库存预警。
- 不做支付网关、代收款、App 内收款或自动发起客户退款。
- 不做 AI 自动开单、聊天识别或图片识别录入。
- 不做自动核账、银行流水读取、支付到账验证或收款截图识别。
- 不做 WhatsApp 自动发送、指定联系人自动投递或聊天平台集成。
- 不做复杂财务系统、税务计算、会计账本、正式发票或正式收据功能。
- 不做部分付款、订金、分期、赊账、商品货款货到付款、部分退款或换货流程；“順豐運費到付”只指买家另付给顺丰的运费。
- 不做物流接口、面单打印、自动物流跟踪或自动签收确认。
- 首版不做订阅、广告、订单额度充值包、复杂会员等级或任意模板编辑器；不为本次文档任务初始化工程、接入购买或编写技术验证代码。

## 4. 核心流程与共同规则

### 4.1 主要使用路径

1. 首次启动显示一屏简洁欢迎页，以“試用示例訂單”为主入口、“直接開始開單”为次入口；可跳过示例，不强制注册、配置店铺或购买 Pro。
2. 示例允许调整商品数量、单价及配送方式，体验自动金额计算和付款通知预览；不进入真实订单记录、不占 Free 额度、不含真实可付款二维码、不允许标为真实已付款。
3. 真实开单使用单页分区，填写买家标识、填写或复用商品并确认金额；历史订单可“複製為新訂單”再核对。即使未设置店铺和收款资料，也可先保存符合创建校验的真实订单，或先看明确标注的非正式预览。
4. 准备正式分享时，再补齐店铺名称和单一可用收款方式；Logo、感谢语、品牌配色均非必填。保存当前订单及收款快照、核对预览后，才进行 PNG 保存、复制付款文字或系统分享。
5. 商家在 App 外确认真实到账后，回到订单中手动标记“已付款”。
6. 商家实际完成发货或面交后，手动登记对应履约状态；需要退款时先在 App 外完成退款，再登记结果。
7. 用户定期主动导出本地备份；App 不宣称存在服务器副本。

### 4.2 共同约束

- 新建及复制的草稿使用新的本机唯一标识，首次成功保存为真实订单时生成新的可读订单编号；两者不可手改。重复点击保存或恢复备份不能造成同一订单被重复建立。
- 真实订单首次创建时必须填写一个买家标识，可用 IG 用户名、买家称呼或自定义客户代号，例如 `@little.shop`、`陳小姐`、`WhatsApp 客人 A`，不要求真实姓名。电话、地址、邮箱、备注等不强制填写，不增加客户管理系统或通讯录权限。
- 买家标识只在首次正式创建真实订单（含复制新单）时校验；草稿可为空，示例使用虚构资料，仅预览不触发该创建校验。缺失时在字段附近提示并保留全部输入，不因新规则自动回填或改写已有历史订单；已有订单编辑继续遵守原权限。
- 配送业务选项为“包郵 / 順豐運費到付 / 面交 / 自訂配送”，费用规则见第 7 节；业务选项不增加新的付款或履约状态。
- 保存前展示可核对的最终金额；真实订单总额必须大于 0。草稿允许不完整；可进入标为“非正式預覽”的体验，但不能输出正式付款通知，具体边界见第 5.3 节。
- 商品数量使用正整数；折扣只支持整单固定金额，首版不增加百分比折扣或优惠券系统。
- 输入边界暂定：每单最多 20 项商品、每项商品名最多 120 个字符、数量 1–999、订单备注最多 500 个字符。开发前验证这些边界是否覆盖真实小店订单，并在发布前确认；超过边界需给出明确提示，不能截断已输入内容后静默保存。
- 未完成输入采用轻量单草稿恢复：返回、切换 App 后恢复已持久化输入；不建立多草稿列表或管理系统。已有草稿时应先提供继续或明确舍弃，不能静默覆盖。草稿不占 Free 创建额度，可舍弃；正式订单继续不提供直接永久删除入口。
- 预览不会自动创建真实订单。第一次成功保存真实订单才占创建额度；创建第 11 张前先说明升级限制，不能让用户填完才首次得知无法保存，详见第 10 节。
- 语言初次跟随系统，非中文回退 English；店铺设置提供语言切换。切换界面语言不改写历史订单内容。

### 4.3 最近 / 常用商品复用

- 在商品明细中打开轻量底部 Sheet，提供最近使用商品、常用商品、名称搜索和“手动输入临时商品”；无商品资料时仍可立即开单。
- 选中商品带入名称和可用默认价格，数量和订单内单价仍可直接修改。不得强制创建 SKU、规格组合或库存记录。
- 订单行保存自己的名称、单价和数量快照。修改复用商品默认价或下一次开单价格，不回写已有订单，也不覆盖当前已经手动调整的订单价格。
- 商家可手动将商品标记为常用；临时输入的商品不自动成为常用商品。最近使用商品可来自真实历史订单或轻量记录，示例商品不进入真实最近 / 常用资料。
- 本单单价独立可改，不自动更新常用商品默认价；只有商家明确执行“更新默认价格”操作才改变该默认值，更新不影响历史订单或当前已经手动调整的价格。不扩展为独立复杂商品管理后台。
- 最近使用条目数量继续作为待验证配置，不在本轮强行固定。

## 5. 页面级功能定义

### 5.0 首次欢迎与示例体验

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 先让 IG Shop 卖家理解开单价值，再在需要正式分享时配置店铺 |
| 核心内容 | 一屏欢迎、Create. Share. Track.、主入口“試用示例訂單”、次入口“直接開始開單” |
| 主要操作 | 试用可编辑示例、跳过示例创建真实订单、结束体验返回真实开单 |
| 关键交互规则 | 示例数量、价格、配送可改并即时计算；预览始终有“示例 / 非真实订单”标识；无真实可付款二维码，无真实订单编号或付款状态操作；不创建真实订单、不计额度、不写入常用 / 最近商品、不允许正式输出 |
| 异常情况 | 中断或离开示例不污染真实草稿；未配置收款资料仍可完成体验；是否保留再次进入示例的入口待确认，不建立额外教程系统 |

### 5.1 订单首页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 让商家快速找到需要跟进的订单，并用明确入口开始新订单 |
| 核心内容 | 待付款订单数量、已付款待履约数量、搜索与状态筛选、最近订单；每条显示订单编号、买家标识、日期、应付总额、付款与履约标签，旧记录缺失标识时如实显示；单草稿继续入口及累计 Free 剩余额度 |
| 主要操作 | 新建订单、继续草稿、打开订单、筛选和搜索、进入店铺设置 |
| 关键交互规则 | 以待处理订单为中心；待付款及已付款待履约优先可见，各分组内按最近创建时间排序；按编号或买家标识搜索；列表不堆叠全部商品和收款说明；历史记录始终可访问；接近用尽时提示累计额度 |
| 异常情况 | 首次无订单时用简洁示例说明下一步，不显示虚构营业额；筛选无结果时提供清除筛选；未配置店铺时给出温和配置提示；额度用完时解释限制并保留全部已有记录 |

首页不设置复杂经营图表。取消、退款及已完成商家履约的订单归入历史；历史判定见第 8 节，不能把“历史”当成第四种付款状态。

导航建议为 Orders / 訂單、My Shop / 我的店舖两个主要 Tab；“新增訂單”为独立主操作，不作为第三个导航 Tab。具体导航布局属于设计验证项。

### 5.2 新建 / 编辑订单页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 用最少重复输入，把已谈妥的交易整理为金额准确的订单 |
| 核心内容 | 单页四分区：买家资料、商品明细、配送与优惠、收款方式；真实首次创建必填买家标识，电话及备注可选；多商品、四种配送选项和默认店铺收款方式；已有订单显示编号、日期及三维状态 |
| 主要操作 | 最近 / 常用商品 Sheet、手动标记常用、显式更新默认价、名称搜索、临时手填、增减商品和数量、直接改本单价；底部显示应付总额、“預覽付款通知”主操作及“儲存訂單”次操作；订单详情次要操作“複製為新訂單”；按权限登记已有订单状态 |
| 关键交互规则 | 单页分区，不做多步骤向导；新建默认一行、数量 1，手填单价不伪造默认值；复用商品可带入其默认价；数量或价格改变即时重算；错误就近提示；键盘不遮挡字段和底部操作；从预览返回保留输入；切换 App 恢复已持久化的单草稿 |
| 异常情况 | 首次真实创建缺买家标识时就近提示并保留全部内容；数量不合法、折扣超限、总额为 0 或超出支持范围时阻止正式保存；保存失败保留草稿；状态不允许编辑时保留原记录并提示；复制不得覆盖既有未完成草稿 |

“預覽付款通知”只进入预览，不自动创建真实订单、不扣额度；“儲存訂單”明确保存真实订单，首次成功创建才计数。正式保存不以已配置店铺收款为前提。预览返回编辑无需重复录入，不将两个操作合成含义不明的按钮。

新订单收款方式默认采用店铺配置，仍可在权限允许时选择单一方式或补齐资料；已保存订单使用自身快照，不能静默回写当前设置。标记付款、发货、退款和取消不混成一个下拉框；状态确认见第 6 节，已付款或已履约后不直接改金额。

#### 5.2.1 複製為新訂單

MVP 在历史真实订单详情的次要操作区域提供轻量“複製為新訂單”，不做批量复制或复杂订单模板。它是新订单的快捷录入方式，不恢复或修改原订单：

| 内容 | 复制结果 |
| --- | --- |
| 标识与编号 | 新的未保存草稿、新的订单标识；正式保存时生成新的订单编号 |
| 商品 | 复用商品名称、数量和单价作为可编辑初始值，不引用当前默认价覆盖原初始价格 |
| 买家 | 买家标识默认留空，首次真实保存前重新填写；不自动带入原买家的其他个人资料 |

## 6. 订单状态模型

### 6.1 三个独立维度

| 维度 | 首版状态 | 含义 |
| --- | --- | --- |
| 订单有效性（订单状态） | 草稿 / 已建立 / 已取消 | 草稿未正式生效；已建立是有效记录；已取消为保留历史的终止记录 |
| 付款状态 | 未付款 / 已付款 / 已退款 | 已付款表示商家手动确认收到整单应付金额；已退款表示商家手动确认已在 App 外退回整单金额 |
| 履约状态 | 待履约 / 已发货 / 已交付 | 寄送类使用已发货，面交使用已交付；两者不同时出现 |

草稿的付款和履约维度尚不适用，不能在草稿上登记付款或发货。“已分享”不是付款状态，“已发货”不是已收款证明，订单状态也不使用“已付款”代替。

首版不额外增加可手动切换的“已完成”订单状态。有效订单在“已付款 + 已发货 / 已交付”后归入历史；该分组只表示商家流程已结束，不表示配送已签收。

四种配送选项与原状态体系的映射已确认：包郵、順豐運費到付、自訂配送统一按寄送类登记“已发货 / 已發貨”；面交登记“已交付”。真实面对面交付应选面交，不增加履约状态，不新增物流服务、自动运费查询或跟踪。示例与非正式预览不产生真实付款或履约记录。

### 6.2 状态变化与约束

| 操作 | 前提 | 结果与限制 |
| --- | --- | --- |
| 正式保存 | 草稿通过金额与字段校验，且有创建额度或 Pro 权益 | 已建立 + 未付款 + 待履约；首次成功保存占用一次新订单额度 |
| 标记已付款 | 已建立 + 未付款 + 待履约；商家确认真实到账 | 付款变为已付款，记录登记时间；分享、导出和二维码被扫描均不能触发此变化 |
| 纠正误标付款 | 已建立 + 已付款 + 待履约，且从未登记履约或退款；确属误标 | 单独确认并填写原因后改回未付款，保留纠正记录；不能用此操作代替真实退款，金额仍保持锁定 |
| 登记发货 / 交付 | 已建立 + 已付款 + 待履约 | 按寄送 / 面交变为已发货 / 已交付；首版不支持未收款先发货或反向切换履约状态 |
| 取消订单 | 已建立 + 待履约，且付款为未付款或已退款 | 主状态变为已取消；保留原金额、付款记录和取消时间，不能重新启用或发货 |
| 登记整单退款 | 已建立 + 已付款；商家已在 App 外实际完成退款 | 付款变为已退款，记录退款金额、登记时间和说明；不自动撤销原发货 / 交付事实 |

- 已付款且未履约的订单，必须先在 App 外退款并登记“已退款”，再取消。不能直接取消并让已收款事实消失。
- 已发货 / 已交付的订单不能取消。可以登记整单退款，保留“已建立 + 已退款 + 原履约状态”，作为已结束的退款历史。
- 已退款订单不能再标记已付款、生成付款通知或登记发货。后续新交易应新建订单；首版不支持部分退款、撤销退款或商品退回管理。
- 已取消订单只读，不能标记已付款、发货或恢复。取消后的外部收款异常需由商家在 App 外核实处理，App 不自动核账。
- 同一次状态操作应完整保存；失败时保留操作前状态，不能出现已显示成功但记录未保存的情况。

### 6.3 编辑权限与金额锁定

| 订单条件 | 允许编辑 | 不允许编辑 |
| --- | --- | --- |
| 草稿 | 所有订单输入字段 | 不允许登记付款、退款或履约 |
| 已建立、未付款、待履约，且从未登记付款或履约 | 商品、数量、价格、折扣、运费、客户及履约信息；显式更新收款资料和模板 | 订单唯一标识、创建时间 |
| 曾登记付款或履约，当前未取消 / 未退款 | 内部备注；按上表执行允许的状态操作 | 商品、数量、单价、折扣、运费及总额；已确认的对外资料和快照 |
| 已退款、尚未取消 | 查看、搜索、导出备份；仅待履约时允许取消订单 | 改金额、改商品、覆盖客户或收款快照、撤销退款或继续履约 |
| 已取消 | 查看、搜索、导出备份 | 改金额、改商品、覆盖客户或收款快照、反向修改终止状态 |

曾登记付款或履约即持续锁定金额，纠正误标也不会重新解锁。发现锁定订单金额错误时，依实际资金和履约情况处理原单，再新建正确订单，不能直接覆盖历史金额。这里的内部备注与发送给客户的订单备注分开，内部备注不进入 PNG。

历史订单的只读限制针对原记录；“複製為新訂單”另建草稿，不是重新启用取消订单、撤销退款或改变原履约事实。当前权益下的新图样式适配也不改变原业务数据，见第 10.3 节。

## 7. 金额计算与历史快照

### 7.1 计算规则

数据层统一使用整数分保存和计算金额；界面按 HKD 显示两位小数。不能用浮点数计算后仅靠显示层四舍五入掩盖误差。

| 项目 | 规则 |
| --- | --- |
| 商品行金额 | 单价（整数分）× 数量（正整数） |
| 商品小计 | 所有商品行金额之和 |
| 折扣 | 整单固定金额，必须 ≥ 0 且 ≤ 商品小计；仅扣商品金额，不抵扣运费 |
| 商家收取的运费 | 必须 ≥ 0，仅计入商家实际向买家收取的配送费；四种配送费用边界见下表 |
| 应付总额 | 商品小计 − 固定折扣 + 商家收取的运费，真实订单必须 > 0 |
| 单价输入 | 允许 0，但订单最终总额须 > 0；最多两位小数，额外精度提示修正，不静默截断 |
| 不合法金额 | 负数、非数字、超出支持范围的值不得保存；支持的金额上限须在开发前验证并于发布前冻结 |

| 配送业务选项 | 商家收取的运费 | 说明与金额边界 |
| --- | --- | --- |
| 包郵 | 0 | 买家不额外向商家付运费，不做商家物流成本核算 |
| 順豐運費到付 | 0 | 买家另向顺丰支付运费，不代表商品货款货到付款，不计入商家应收总额；付款通知清楚说明 |
| 面交 | 0 | 无商家配送费；保持付款后才登记交付的原状态约束 |
| 自訂配送 | 商家填写的非负金额 | 可填写配送说明和商家收取的运费；不接入物流或预测承运商费用 |

从自訂配送切换为其他三种时，如已有运费须明确提示并清零，避免旧运费残留。固定折扣不得超过商品小计；首版不支持百分比折扣、优惠券、满减或会员定价。

核对示例：HK$88.50 × 2，加 HK$39.90 × 1，商品小计为 HK$216.90；折扣 HK$16.90、自訂配送收取运费 HK$30.00，应付总额为 **HK$230.00**。对应整数分计算为 21,690 − 1,690 + 3,000 = 23,000。同单改为順豐運費到付时商家运费为 0，应付 **HK$200.00**，顺丰费用由买家另付。

首版不另加税费、手续费、汇率或隐藏费用。编辑页、订单列表、PNG 和备份恢复后的金额必须一致。

### 7.2 历史订单快照规则

- 正式保存时保留该订单的商品名称、数量、单价、固定折扣、商家运费、总额、买家与配送选项 / 履约信息、当时可用的店铺名称、Logo、感谢语、收款文字、选定二维码和图片语言 / 模板及允许的强调色选择；未配置资料可为空，不伪造完整快照。
- 商品价格变更不影响历史订单。最近 / 常用商品的默认价仅用于选入新订单，不得通过商品现价回算旧单；订单内改价不自动回写，常用商品默认价只通过商家明确更新操作改变。
- 店铺改名、更换 Logo、替换收款二维码或切换界面语言，不自动回写已有订单。
- 尚未付款且从未登记付款 / 履约的有效订单，可由商家明确选择更新订单或收款资料；更新后旧预览失效，必须重新生成，提示已发送的旧图不会自动更新。
- 金额锁定、取消或退款后保留原快照。不能用当前配置填补旧订单缺失的收款图片并假装它一直属于旧单。
- 源相册图片被删除不应导致已保存资料丢失；若 App 本地副本确实缺失，则按异常规则提示，不得静默分享缺失内容。
- 业务快照与独立 PNG 文件分别对待：Pro 退款 / 撤销不改金额、商品、状态、历史记录、原模板选择或强调色快照，也不自动修改已生成、保存或发送的 PNG。原 PNG 若已保存为独立文件则保留原貌；未持久保存或已丢失时不能声称原图片文件仍在。符合输出条件时可按当前权益生成新图，但不覆盖原快照或原 PNG，规则见第 10.3 节。

## 8. 取消、退款与历史订单

### 8.1 取消与记录保留

取消仅允许“待履约，且付款为未付款或已全额退款”的有效订单。取消前展示订单编号、金额和当前付款状态，并说明保留历史且不能恢复；可记录取消原因。

取消不删除记录、不清空金额、不返还 Free 已使用的新订单额度，也不自动修改真实资金情况。已付款且未退款时阻止取消，并解释先完成外部退款与登记的要求。

### 8.2 首版退款边界

只支持**手动登记整单退款**，退款金额固定等于原订单应付总额，包含已计入总额的商家运费。順豐運費到付中买家另付承运商的费用不在该总额或退款登记内。商家实际只退部分金额时不能谎报为整单退款，首版不承接该业务流程。

登记前必须明确提示“请先确认已在收款渠道完成退款”，并二次确认金额。OrderMori 不发起退款、不连接银行或支付工具，也不把“登记已退款”描述为退款已经由 App 执行。

### 8.3 历史展示

以下任一条件成立即归入历史：已取消；已退款；或已付款且已发货 / 已交付。已退款且待履约的订单也属于历史，不能继续履约；仍可按第 6 节取消。

历史保留原商品、金额、订单编号、创建时间、当前三维状态，以及已登记的付款、退款、取消和履约时间。退款订单同时展示原应付金额和整单退款金额，不将原总额改成 0。状态纠正记录只需在订单详情可查，不建立复杂审计或财务报表。

## 9. PNG、二维码与分享边界

### 9.1 付款通知内容与排版

- PNG 使用纵向排版，优先适合手机阅读，高度依内容动态变化。以 1080px 宽度作为初步验证目标，最终尺寸与最长订单边界需通过真机分享验证，不能用无限长图片规避可读性和内存限制。
- 展示店铺名、可选 Logo、订单编号 / 日期、商品与数量、单价与行金额、小计、固定折扣、商家运费、突出的应付总额、配送说明、选定的单一收款方式；可选买家称呼、对外备注与感谢语。順豐運費到付不混入商家应收金额。
- 私人联系方式、配送地址和内部备注不默认输出到付款 PNG。首版不增加地址排版或地址公开开关。
- 商品名和备注按行展开，不用省略号隐藏应付款项，也不缩小到无法阅读；总额、二维码及其说明不可截断。
- 正式付款前使用明确标题“付款通知 / Payment Notice”，保留“仅供付款通知，并非正式收据或已收款确认”的对应语言说明。不得显示暗示资金已到账的收据措辞或标记。
- 图片语言首次按当前界面语言确定，保存在订单中；之后切换 App 语言不会静默改写旧图。
- 黑白极简和韩系柔和均为 Free 可用，均支持商家 Logo、动态高度、中英文及自适应收款资料。Free 底部保留小型 `Made with OrderMori`；Pro 可移除该标记并选择少量设计好的品牌强调色，不移除付款通知说明、不修改二维码或损害文字对比。

### 9.2 二维码来源与展示

- **不自行生成未经验证的 PayMe / FPS 收款二维码**，不拼接付款码内容，不声称可自动把订单金额写入官方收款码。
- 二维码由商家从官方支付工具或官方渠道取得并上传。商家负责确认收款对象正确；App 仅保存和展示，不声称验证收款账户或实际到账。
- 保留原图比例、清晰度和二维码周围必要留白，不染色、不反转、不拉伸、不覆盖 Logo、不套装饰滤镜；两款模板遵守相同规则。
- 正式验收须使用商家授权的测试二维码，经实际生成、分享和接收后扫码验证。涉及转账时由测试人员自行核实，不执行真实付款作为自动化验证。
- 二维码不可读或丢失时，不生成依赖该二维码的付款通知。商家可为仍可编辑的未付款订单补选有效官方图片，或明确改选已经配置的文字收款方式。
- 如上传的二维码可能含固定金额，必须提醒商家确认收款对象及该码适用于当前订单；不能默认码中金额等于订单总额，也不声称已自动识别或校正金额。

付款通知只采用商家选定的单一收款方式，正式采用以下自适应规则：

| 情况 | 商家提供的资料 | 展示与输出规则 |
| --- | --- | --- |
| A | 官方二维码 + 有效文字资料 | 二维码为主要视觉内容，同时展示同一方式对应的 FPS ID 等必要文字资料 |
| B | 只有官方二维码 | 清晰展示原码及已知的方式名称，不虚构不存在的文字收款资料 |
| C | 只有有效文字资料 | 仅展示清楚的文字收款区域，不显示空白二维码框或假二维码 |
| D | 没有任何可用收款资料 | 可保存真实订单、可看明确标注的非正式预览；禁止正式分享、PNG 输出和付款文字复制，提供补齐资料入口 |

“有效文字资料”指所选方式所需信息齐备、可读并经商家核对，不表示 App 已验证真实账户或到账；必要资料已按下节确认，具体格式与长度仍需技术设计验证。二维码损坏不能静默当作有效码；即使另有有效文字，也需由商家明确改选文字展示后再正式输出。

#### 9.2.1 收款方式的必要资料

| 收款方式 | 资料规则 | 边界 |
| --- | --- | --- |
| FPS | 文字收款可配置一种适用的官方标识：FPS ID、支持 FPS 收款的手机号或邮箱；商家必须确认其关联自己的实际收款账户。银行或官方支付工具生成的 FPS 二维码可与同一方式的文字标识同显 | A / B / C 展示继续适用，只有官方二维码时不虚构文字；不得仅凭 FPS ID 自行生成未经验证的支付二维码 |
| PayMe | 首版优先商家上传的官方 PayMe 收款二维码；其他资料只有在属于官方支持、且经商家确认适用的类型时才按其实际类型展示 | 任意电话号码、普通网页链接或未经确认文本不算有效 PayMe 收款资料；不自动生成、解析或验证 PayMe 支付码；无法确认适用时不能视为完成正式输出配置 |
| 银行转账 | 首版采用文字展示，必须有银行名称、收款人名称、银行账号 | 字段格式和长度在技术设计时用真实香港银行资料验证；不声称 App 已验证账户所属人 |

每张通知只选择一个明确收款方式，二维码与文字必须属于同一方式、同一收款账户；不混合不同账户或商家的资料，不虚构缺失字段，不上传收款资料到开发者服务器。商家自行确认正确性；可能含固定金额的收款码需核对适用性，App 不自动核实到账，不改变现有付款状态模型。

按选定方式及实际资料类型校验必要字段；资料不完整或无法确认有效时，可保存符合创建条件的订单并进行非正式预览，但禁止正式输出无效付款通知。二维码单独有效的 B 情况仍成立，不因该方式同时支持文字就捏造或强制补出不存在的文字资料。

### 9.3 分享边界

分享通过 iOS 系统分享面板，用户自行选择 App 和联系人。OrderMori 不承诺自动发送到指定联系人、不控制聊天工具压缩、不获取客户是否已查看，也不将分享面板返回成功等同于送达。

支持保存 PNG 与复制付款文字；两者和正式分享采用同一订单、金额、状态及收款有效性边界。复制成功只表示写入剪贴板，不代表已发送。保存目标与权限提示需在设计中确认；用户取消保存或拒绝权限时保留订单。不得利用保存或复制绕过示例、非正式预览或历史已付款限制。

用户取消分享时订单保持原状；分享失败允许重试，不重复创建订单或消耗新订单额度。没有网络时可生成图片并打开系统面板，实际外部发送是否成功由接收 App 决定。无论分享、保存图片还是扫码，付款状态均不自动变为已付款。

### 10.1 免费额度规则

| 事件 | 是否消耗一次创建额度 |
| --- | --- |
| 示例订单、未保存草稿或仅看预览 | 不消耗 |
| 第一次成功创建真实订单 | 消耗 1 次；同一订单重试保存不重复计数 |
| 编辑已有订单、跟进状态、重新生成或分享 | 不消耗，仍须符合原有状态约束 |
| 复制历史订单并成功保存为新的真实订单 | 消耗 1 次，不能复用原标识绕过计数；入口及复制字段见第 5.2.1 节 |
| 取消、退款或删除已创建订单 | 不返还已用额度；这条计数规则不代表新增正式订单删除入口 |

- 保存时再次校验权益和累计额度，失败保留已持久化草稿；不重复创建、不重复扣额。示例仍可体验，但不能用于生成真实订单绕过限制。
- 额度用尽后仍可查看历史、跟进已有订单、更新允许的付款 / 履约状态、访问必要历史信息、备份恢复，以及按原状态约束分享已有未付款订单；不锁住第 10 张订单。
- 本地累计计数不依赖当前订单表行数，不按时间或月份重置。取消或移除业务记录不能回退累计创建记录。
- 备份包含累计创建与额度记录。恢复当前本地安装的数据档案时，不能降低已记录累计次数，也不因恢复本身新增计数；先验证备份版本、数据完整性和订单唯一标识，再使用正常、可信的额度记录，不能直接信任未经校验的计数字段。

| 3 | 10 | 10 |
| 10 | 10 | 10 |

OrderMori 无需账号、不依赖自建后端；不声称能绝对阻止卸载重装或更换设备重置额度，不为此增加账号系统、设备指纹、云端额度服务器或复杂反作弊系统。备份文件也不作为 Pro 购买凭证。

OrderMori Pro 不设按月或按年到期时间，无需订阅续费；除 Apple 已确认退款、撤销等特殊交易情况外，正常购买权益不会因为时间经过而失效。这是对现有 Non-Consumable 一次性买断规则的澄清，不新增订阅、周期授权验证或其他商业化机制。

Pro 权益为无限创建、移除品牌标记、品牌强调色。配色仅提供少量经设计的预设，作用于允许的品牌视觉区域；不改变官方二维码图像、颜色或留白，不削弱金额与文字对比，不提供任意模板编辑器。

必须支持购买与恢复购买，权益根据有效 Apple 购买记录判断。已确认有效的本机 Pro 权益支持合理离线使用；首次购买或新设备恢复需网络和平台服务。失败、取消、待处理或无法确认时不虚假解锁，也不因短暂离线抹去最后已确认权益。明确收到退款或撤销、失效结果后回到 Free，但保留所有订单和备份能力。

恢复数据与恢复购买是两个独立操作：备份内的“曾是 Pro”信息不授予购买权益。恢复购买无匹配记录、网络失败或平台异常时，说明原因并提供重试。客户订单退款与 Pro 买断购买退款是不同事项，不共用业务状态。

- 不删除任何已有订单，不修改订单金额、商品、状态、历史记录、原模板选择或品牌强调色快照，也不自动修改已生成、保存或发送的 PNG。独立保存的原 PNG 保留原貌；原图未持久保存或已丢失时不能假装文件仍在。
- 只有仍符合第 5.3 节正式输出条件的未付款订单，才可重新生成付款通知；新输出依据当前有效权益，不把原订单快照改成新的导出样式。

| --- | --- |
| 有效 Pro | 允许移除品牌标记及使用 Pro 预设强调色；仍保留付款通知说明与二维码安全规则 |

已付款、已退款、已取消订单仍不生成新的催款式付款通知；不为权益撤销新增正式收据、已付款确认单或其他图片类型。

## 11. 本地备份与恢复

- 备份由用户主动导出为文件，包含单草稿、真实及历史订单、状态与必要变更记录、历史快照、最近 / 常用商品资料、店铺设置、Logo、感谢语、二维码和文字收款资料、模板及预设色选择、累计额度记录；不混入示例，不只导出图片路径。
- 导出只保存一份可恢复的本机资料副本，不包含支付登录凭证或可直接授予 Pro 的权益。明确提示备份含客户及收款资料，应由用户妥善保管。
- 用户可通过系统文件选择或分享保存到自己选择的位置；这不构成 App 的自动云同步。不配置自动上传、服务器备份或跨设备后台任务。
- 首版只支持整体替换恢复，不做合并订单。恢复前校验文件格式、备份版本、数据完整性、订单唯一标识与必要图片，展示备份时间和订单数量，提示将替换当前业务数据，并建议先导出当前数据；未经校验的计数字段不可直接采信。
- 整体替换仅针对备份涵盖的业务资料；已确认本机购买权益不被备份覆盖。当前安装数据档案的累计次数不能回退，使用经验证本地 / 备份记录按第 10.1 节较高值规则处理，不简单依据恢复后订单行数计算，也不因恢复本身消耗新额度。事务与具体恢复合并实现留到技术设计。
- 确认后恢复全部成功才切换为恢复结果；校验或写入失败保留原业务数据。损坏、版本不支持或图片不完整的备份拒绝恢复，不做无提示的部分导入。
- 恢复超出免费额度的备份时允许恢复全部记录并提示限制，不能以升级为前提扣住历史。换设备恢复业务数据后，Pro 仍需通过恢复购买确认。
- 若备份包含已持久保存的独立 PNG，恢复时保留原貌；未包含原文件时不得声称已恢复该原 PNG。符合状态约束时重新生成的图片按当前权益输出，不修改历史快照。

视觉与体验细化见 [UI_DIRECTION.md](./UI_DIRECTION.md)。两份文档均为 Review Draft；本节保留产品质量要求，UI 基线不改变第 6–11 节业务规则。

### 12.1 整体视觉目标

OrderMori 应让用户感到**清爽、精致、专业、有品质感**。面向小商家不意味着廉价；界面应比普通工具 App 更好看，且足够舒适，让用户愿意长期停留和重复使用。

美观必须服务任务：金额准确、状态可辨、分享有信心，比堆砌装饰更重要。通过少数界面中稳定的字体、间距、细节和反馈建立品牌，而非靠大面积装饰吸引注意。

### 12.2 设计风格方向

- 已确认视觉方向为 **Premium Minimal — Warm White & Charcoal**：暖白 + 深炭黑，专业极简，精致但信息紧凑；偏 iOS 原生审美，优先沿用熟悉的返回、表单、Sheet、选图和系统分享方式。
- 使用适度品牌色和克制的装饰，不花哨；品牌识别集中在细节和付款模板中。
- 优先使用白色容器与轻分隔线进行信息分组，减少无意义独立卡片与嵌套；每屏有清楚标题、有效业务信息和主要操作，紧凑不靠缩小字体实现。
- 重视留白、字体层级、行距、对齐、圆角和轻量阴影。阴影用于说明层级，不造成厚重后台感。
- 金额采用易比较的数字排版，HKD 币种与小数位清楚；正文和金额字体以阅读为先，不使用影响识别的装饰字。
- 页面不应有明显的“开发者工具感”或“管理后台感”：避免拥挤数据表、密集按钮、实现术语和调试信息。

### 12.3 关键体验要求

| 页面 / 场景 | 必须达到的体验 |
| --- | --- |
| 首次体验 | 一屏欢迎、示例主入口、真实开单次入口；先体验后配置，无强制注册或购买 |
| 新建订单 | 单页四分区、最近 / 常用商品 Sheet、合理默认值、就近校验；底部总额与预览主操作清楚，保存为独立次操作；键盘避让、返回和中断恢复已持久化单草稿 |
| 首页列表 | 编号 / 客户、总额、当前待办一眼可见；标签克制，避免每张卡片塞满明细；空状态有明确下一步 |
| 付款图片预览 | 暖白 App 背景与纯白通知画布分离；正式预览忠实于导出，长明细可滚动 / 放大；收款资料按四种情况适配，缺资料明确非正式预览，不显示假码 |
| 店铺设置 | 首次必填与可选内容分组，解释为什么要上传收款码；基础配置目标暂定不超过约 3 分钟，不包含寻找官方二维码的时间 |
| 金额与状态 | 总额突出且易读；付款和履约分别标记，文字与颜色共同表达；标签清晰但不过于刺眼 |
| 保存、生成、分享 | 主操作名称直接表达结果；保存成功、处理中、失败、取消各有准确反馈；不能把“生成”反馈成“已发送” |
| 错误与限制 | 指出问题和可执行的修复方法，保留输入；升级提示不阻断历史和备份 |

### 12.4 首版两个模板

| 模板 | 视觉方向 | 共同质量要求 |
| --- | --- | --- |
| 韩系柔和 | 暖白或低饱和柔和底色、精致间距、轻盈分组，呈现亲切但专业的小店气质 | 美观、易读、品牌感强，适合商家发送给客户；金额和二维码不因装饰失去对比 |
| 黑白极简 | 清晰黑白对比、克制线条、整齐对齐和干净留白，强调专业与可信 | 与柔和模板拥有相同信息完整性；不是把同一模板简单去色 |

两款模板均需在最长支持商品名、最多商品行、长备注、可选 Logo 缺失及中英文内容下验证。二维码保留清楚白底和必要留白；长商品名换行后，价格、总额及扫码区域仍有稳定位置，不能出现覆盖、挤出或裁切。

两款均为 Free 可用、均支持 Logo 和自适应收款区域。Pro 只在允许区域增加少量预设强调色并可去除品牌标记；不设 Pro 专属模板，不以去掉付款通知说明作为付费权益。

### 12.5 可读性、可访问性与反馈

- 核心内容和操作在最小支持 iPhone 屏幕、大字号及键盘打开时仍可阅读和触达；若支持 iPad，表单合理限宽而非铺满；首发 iPad、设备及系统范围在开发前确认。
- App 正文随系统字号调整，不能因大字号隐藏金额或按钮；交互触控区域目标不小于 44 × 44 pt，不把静态 PNG 的字号适配与界面适配混为一谈。
- 普通正文与背景的对比度目标至少 4.5:1；状态不能只依赖颜色，配合文字。主要按钮、输入和状态标签使用一致的视觉规则。
- 关键表单、金额、状态和操作提供有意义的辅助阅读标签，VoiceOver 阅读顺序符合业务顺序；错误提示能被发现。
- 动效简短、可减少，用于解释状态和操作反馈；不以开场动画、过度弹窗或装饰动画打断高频开单。
- English 和繁體中文（香港）分别检查文字长度、换行及常用说法。界面文案面向商家，不暴露文件路径、字段名或内部错误堆栈。

### 12.6 后续设计原则

后续开发不为赶工牺牲核心界面质量。先把少数页面做精，再决定是否增加功能；交互与视觉质量本身是产品竞争力的一部分。遇到时间冲突时优先缩减非核心范围，不以粗糙首页、难用开单或不好看的付款图片作为完成标准。

本节定义产品质量方向；初始色板和尺寸候选集中在 UI_DIRECTION，不在本文另设一套设计令牌。首版优先打磨浅色主题，深色主题待评估；本次不产出高保真稿、组件代码或页面实现。

## 13. 异常场景与预期处理

| 场景 | 预期处理 |
| --- | --- |
| 未设置收款方式 / 店铺名称 | 可保存真实订单与草稿、看标明的非正式预览；正式输出前定位补齐，不显示虚构账户或空二维码框 |
| 二维码丢失、损坏或过于模糊 | 阻止依赖该码的生成和分享；保留订单；可编辑未付款订单允许补选官方图或明确改选已有有效文字方式；锁定历史只可通过完整备份恢复原图 |
| 本地 Logo / 预览图片文件丢失 | Logo 缺失时说明并由用户确认是否在可编辑订单中移除；原 PNG 未持久保存或已丢失须如实说明；仅符合正式输出条件时可按当前权益重生成新图，不冒充原文件，不覆盖锁定快照；已付款等仍不生成新催款图 |
| 商品名过长或超过商品行上限 | 输入时展示边界；范围内正常换行，超限说明后阻止保存，不静默截字或导出半张图片 |
| 总额为 0、负数或折扣超限 | 显示费用拆分和具体问题，阻止正式保存 / 生成，保留草稿 |
| 输入含无效精度或超出金额支持范围 | 定位对应字段，要求修正；不能四舍五入后偷偷改变商家输入 |
| 生成 / 分享失败、用户取消分享 | 允许重试或返回；不重复创建订单、不增加额度、不改付款状态，不声称客户已收到 |
| 离线分享、购买或恢复购买 | 可离线生成和打开分享面板；说明外部发送及购买服务可能需要网络；保留最后已确认权益和当前输入 |
| 未购买 Pro 且已创建 10 张真实订单 | 在第 11 张新建 / 复制入口预先说明升级限制，保存时复核；保留已有草稿，历史、状态管理、符合原约束的分享及完整备份继续可用，不等待填完才告知 |
| 购买取消 / 待处理 / 失败 | 分别提示当前结果，不错误激活、不自动反复购买，保留原操作上下文 |
| 恢复购买失败或无匹配记录 | 给出可理解的原因及重试入口，不授予未知权益，也不删除订单 |
| 备份损坏、版本不兼容或图片不全 | 恢复前拒绝并解释；不部分覆盖当前数据，允许重新选择文件 |
| 备份导出中断或磁盘空间不足 | 保留本机数据，不把半成品描述为成功备份，说明清理空间或重试 |
| 试图取消已付款未退款 / 已发货订单 | 根据状态说明先退款登记或只能保留履约历史，不能直接取消 |
| 试图修改已付款、已退款、已取消订单金额 | 清楚显示锁定原因和允许的后续操作，不提供绕过状态的金额编辑 |
| 恢复超量或含 Pro 品牌外观的备份 | 全部保留并可查看，两款模板仍可用；累计额度按已校验记录的较高值规则不回退，备份不授予 Pro；符合条件的新图按当前权益输出，不覆盖原图或外观快照 |
| 最近 / 常用商品为空或默认价格无效 | 可直接手动输入临时商品；不强制建目录、不伪造价格；本单改价不更新默认价，临时商品不自动标为常用 |
| 切换 App 后返回开单 | 恢复已持久化的单草稿及选项；无法恢复时如实说明，不把示例或其他订单覆盖到草稿 |
| 二维码可能包含固定金额 | 提醒确认适用于本单金额和对象；不默认等额、不自动改码 |
| 只有文字收款资料 / 只有二维码 | 分别采用自适应 C / B 规则，不显示空白码框或编造收款文字 |
| 顺丰运费到付误填为商家运费 | 明确这是买家另付给顺丰的运费，商家收取运费为 0；切换方式时提示并清除残留费用 |
| PNG 保存或复制付款文字失败 | 保留订单并给出权限 / 重试提示；不误报发送或收款成功，非正式预览不能借此绕过正式输出条件 |
| 首次真实保存缺买家标识 | 就近提示填写 IG 用户名、买家称呼或客户代号，保留所有输入；草稿、示例及仅预览不做真实创建必填校验，不索取额外个人资料 |
| 复制历史订单 | 只生成新标识草稿，买家清空、折扣清零、配送和当前收款重核；保存前可检查商品价格总额；不复制原状态或时间，不覆盖原单；额度耗尽在入口先说明 |
| FPS / PayMe / 银行转账资料不完整或不适用 | 按第 9.2.1 节定位缺失内容，保留订单与非正式预览，但禁止输出无效通知；不把任意手机号或网页链接当作有效 PayMe 资料 |
| Pro 已明确撤销后重新生成旧单图片 | 先提示将使用免费版样式；仅符合输出状态的订单生成带 Free 标记及模板默认色的新图；保留原图与业务快照，已付款等不输出新催款图 |
| 备份计数未经校验或疑似损坏 | 不直接信任计数字段；完成版本、完整性及订单唯一标识校验后才按可信记录恢复；失败保留原业务数据与已记录用量，不凭订单行数重置额度 |
