## 1. 产品定位

### 1.1 OrderMori 是什么

OrderMori 是面向香港及未来国际市场的小型商家的订单管理和付款通知工具。商家在手机上手动建立订单、生成清晰的付款通知图片，通过系统分享交给客户，并自行登记付款和履约进度。

产品解决“小店在聊天中接单，商品、金额和收款说明零散，容易漏记或重复确认”的问题。首版采用 HKD 单币种，不承诺其他地区的支付支持、多币种或汇率换算。全球可下载与完整适配各国业务分开处理，国际化范围待后续验证。

### 1.2 目标用户与核心场景

| 用户 / 场景 | 核心需求 |
| --- | --- |
| 通过 WhatsApp、社交平台或线下接单的香港个体商家、小店主 | 把已经谈好的商品、数量、金额快速整理成一张订单 |
| 手作、预订、代购等低复杂度业务的单人经营者 | 发出美观易读的付款说明，再手动跟进收款和发货 |
| 不需要大型电商后台的小型服务提供者 | 清楚表达项目费用、折扣和运费，保留本机历史记录 |

典型使用场景是“一人、一部手机、本机经营记录”。客户无需安装 App；首版没有商家账号注册、客户账号或客户地址簿系统。

### 1.3 商业目标

- 让商家愿意反复使用快速开单和分享流程，以清楚、美观、可靠的付款图片建立产品价值。
- Free 提供真实可用的完整基础流程，Pro 通过更高使用额度和视觉选择形成一次性买断价值。
- 在扩大功能前，先验证商家是否能独立完成开单、是否愿意把图片发给客户，以及是否愿意购买 Pro。
- 易用性目标暂定为：完成基础店铺配置后，熟悉流程的商家可在约 60 秒内保存并准备分享一张包含 3 项商品的简单订单；测试时需说明输入内容和设备条件。这是待验证目标，不是已测结果。

### 1.4 项目独立性

OrderMori 与 HomeyPaw 完全独立，不共享产品代码、业务数据、账号体系、数据库、后端或商业化配置。不复制其业务设计；本 PRD 不产生对其他项目的修改要求。

## 2. MVP 范围

| 范围 | 首版交付边界 |
| --- | --- |
| 订单首页 | 查看、简单搜索和筛选本机订单，区分待处理与历史，进入新建或已有订单 |
| 快速开单 | 手动输入商品、整数数量、单价、整单折扣和运费；支持草稿及受约束的编辑 |
| 付款图片预览与分享 | 两款模板：韩系柔和、黑白极简；预览纵向 PNG，通过 iOS 系统分享面板分享 |
| 店铺设置 | 店铺名称、可选 Logo、手动收款说明及商家上传的官方来源收款二维码 |
| 本地备份恢复 | 用户主动导出备份并从文件恢复，包含订单、设置和必要图片 |
| Free / Pro | 免费额度、模板权益、一次性购买入口和恢复购买；具体额度与定价见第 10 节 |
| 基础语言与离线体验 | English、港式繁体中文；订单、设置、预览、已有权益和本地文件操作可离线使用 |

首版的商品来自订单内手动输入，不建立独立商品目录、库存或客户管理模块。购买及恢复购买需要网络和平台服务，不属于离线承诺。

## 3. 明确不做事项

- 不做云同步、自动云备份、跨设备实时同步或账号登录体系。
- 不做多人协作、员工权限、团队共享或网页管理后台。
- 不做复杂库存、采购、商品规格管理或库存预警。
- 不做支付网关、代收款、App 内收款或自动发起客户退款。
- 不做 AI 自动开单、聊天识别或图片识别录入。
- 不做自动核账、银行流水读取、支付到账验证或收款截图识别。
- 不做 WhatsApp 自动发送、指定联系人自动投递或聊天平台集成。
- 不做复杂财务系统、税务计算、会计账本、正式发票或正式收据功能。
- 不做部分付款、订金、分期、赊账、货到付款、部分退款或换货流程。
- 不做物流接口、面单打印、自动物流跟踪或自动签收确认。
- 首版不做订阅；不为本次文档任务初始化工程、接入购买或编写技术验证代码。

## 4. 核心流程与共同规则

### 4.1 主要使用路径

1. 首次进入首页，可先体验填写订单；生成付款通知前，引导完成店铺名称及至少一种可用收款方式。
2. 新建订单，填写至少一项商品，确认数量、单价、折扣和运费，保存为正式订单。
3. 在付款图片预览页核对金额、商品和收款资料，选择有权使用的模板，再打开系统分享面板。
4. 商家在 App 外确认真实到账后，回到订单中手动标记“已付款”。
5. 商家完成实际发货或自取交付后，手动登记对应履约状态；需要退款时先在 App 外完成退款，再登记结果。
6. 用户定期主动导出本地备份；App 不宣称存在服务器副本。

### 4.2 共同约束

- 订单有本机唯一、不可手改的标识和可读订单编号。新建、重复点击保存及恢复备份不能造成同一订单被重复建立。
- 客户称呼、联系方式及配送信息按业务需要选填，不强制读取通讯录。履约方式仅区分“配送”和“自取”。
- 保存前展示可核对的最终金额；正式订单总额必须大于 0。草稿允许暂时不完整，不能用于生成或分享付款通知。
- 商品数量使用正整数；折扣只支持整单固定金额，首版不增加百分比折扣或优惠券系统。
- 输入边界暂定：每单最多 20 项商品、每项商品名最多 120 个字符、数量 1–999、订单备注最多 500 个字符。开发前验证这些边界是否覆盖真实小店订单，并在发布前确认；超过边界需给出明确提示，不能截断已输入内容后静默保存。
- 未保存的输入应在本机保留为草稿；返回或中断不能无提示丢失。草稿不占 Free 正式订单额度，允许删除草稿；正式订单不提供直接永久删除入口。
- 语言初次跟随系统，非中文回退 English；店铺设置提供语言切换。切换界面语言不改写历史订单内容。

## 5. 页面级功能定义

### 5.1 订单首页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 让商家快速找到需要跟进的订单，并用明确入口开始新订单 |
| 核心内容 | 订单编号、客户称呼（如有）、日期、应付总额、付款与履约标签；草稿、待付款、待履约、历史的简单筛选；按编号或客户称呼搜索；Free 剩余额度提示 |
| 主要操作 | 新建订单、继续草稿、打开订单、筛选和搜索、进入店铺设置 |
| 关键交互规则 | 待付款、待履约优先可见，各分组内按最近创建时间排序；列表不堆叠全部商品和收款说明；打开订单复用订单查看 / 编辑界面；历史记录始终可访问 |
| 异常情况 | 首次无订单时用简洁示例说明下一步，不显示虚构营业额；筛选无结果时提供清除筛选；未配置店铺时给出温和配置提示；额度用完时解释限制并保留全部已有记录 |

首页不设置复杂经营图表。取消、退款及已完成商家履约的订单归入历史；历史判定见第 8 节，不能把“历史”当成第四种付款状态。

### 5.2 新建 / 编辑订单页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 用最少重复输入，把已谈妥的交易整理为金额准确的订单 |
| 核心内容 | 订单编号和日期、可选客户信息、配送 / 自取、商品行、折扣、运费、应付总额、可选备注；已有订单展示三类状态 |
| 主要操作 | 添加 / 移除商品行、填写数量和单价、保存、继续预览；已有订单可按状态标记付款、登记履约、取消或登记退款 |
| 关键交互规则 | 新建默认一行商品、数量默认 1；单价不预填虚假金额；金额实时预览、保存时再次校验；字段错误定位到对应输入；键盘不遮挡总额和保存；只读字段必须解释锁定原因 |
| 异常情况 | 必填缺失、数量不合法、折扣超限、总额为 0 或超出支持范围时阻止正式保存并保留输入；保存失败时草稿仍可恢复；状态已不允许编辑时保留原记录并提示 |

保存成功后清楚展示“预览付款图片”入口。标记付款、发货、退款和取消不得混成一个状态下拉框；需要用户确认的状态变化见第 6 节。已付款或已履约后不提供直接改金额的入口。

### 5.3 付款图片预览页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 让商家有把握地分享一张专业、清楚、值得发给客户的付款通知 |
| 核心内容 | 与最终 PNG 一致的纵向预览、店铺信息、订单编号、商品明细、费用拆分、突出显示的 HKD 总额、已选收款方式、二维码（如有）及付款通知说明 |
| 主要操作 | 切换有权使用的模板、选择已配置的收款方式、返回编辑、生成 PNG 并打开系统分享面板 |
| 关键交互规则 | 先显示完整预览再允许分享；图片生成期间防止重复操作；滚动可查看全文，支持查看二维码和长内容细节；分享使用当前已保存订单；分享或关闭分享面板均不标记已付款 |
| 异常情况 | 收款方式缺失、二维码或 Logo 文件损坏、生成失败、设备空间不足时说明原因并允许重试；用户取消分享不显示成功送达；无 Pro 权益时清楚解释模板限制 |

只有“已建立 + 未付款 + 待履约”的有效订单可新生成或分享付款通知。订单转为已付款、已退款或已取消后，可查看已有历史预览，但分享付款通知的入口关闭，并在 App 内明确显示现有状态。App 无法撤回已分享给客户的旧图片。

模板或收款方式的变更须按第 6 节权限保存到订单后再生成；保存失败时不能分享未落盘的版本，不能借切换模板改写锁定快照。

### 5.4 店铺设置页

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 帮助商家容易地完成第一次配置，并管理本机经营资料 |
| 核心内容 | 店铺名称、可选 Logo、收款方式及说明、官方来源收款二维码、界面语言、备份 / 恢复入口、Free / Pro 权益和恢复购买入口 |
| 主要操作 | 保存设置、上传 / 替换图片、检查收款资料、导出备份、恢复备份、进入升级或恢复购买 |
| 关键交互规则 | 将“生成付款通知前必需”与“可稍后补充”分组；店铺名称必需，Logo 可选；生成付款通知前至少有一种可用收款方式；选图后预览并由商家确认二维码来源和收款对象；保存后反馈清楚 |
| 异常情况 | 未授权访问图片时给出可行选图提示；文件不支持、过大或不可读时保留旧配置；备份或恢复失败时保留原数据；切换语言不清空未保存内容 |

收款方式允许商家手动填写 PayMe、FPS 或银行转账等说明，不连接支付账户、不验证到账。二维码为可选附件；每张付款图片只展示一个已选方式，避免混淆收款对象。修改店铺配置只影响后续订单，已有订单按快照规则处理。

### 5.5 Pro 升级入口

| 项目 | 定义 |
| --- | --- |
| 页面目标 | 清楚说明买断后得到什么，以及未购买时还可继续做什么 |
| 核心内容 | 当前 Free / Pro 状态、免费额度、两方案对比、一次性购买说明、平台实际可用的本地化价格、恢复购买入口 |
| 主要操作 | 购买 Pro、恢复购买、关闭并返回原操作 |
| 关键交互规则 | 入口来自设置、额度用尽或 Pro 模板；购买前不假装解锁；价格未取得时不显示虚构价格；购买成功后回到原流程，保留原订单和输入 |
| 异常情况 | 无网络、购买取消、购买待处理、平台失败、没有可恢复的购买等情况分别提示；未知状态不得显示为成功；允许重试或返回继续使用 Free |

不使用倒计时、虚假折扣、全屏强迫购买或遮住历史订单的升级提示。

## 6. 订单状态模型

### 6.1 三个独立维度

| 维度 | 首版状态 | 含义 |
| --- | --- | --- |
| 订单状态 | 草稿 / 已建立 / 已取消 | 草稿未正式生效；已建立是有效记录；已取消为保留历史的终止记录 |
| 付款状态 | 未付款 / 已付款 / 已退款 | 已付款表示商家手动确认收到整单应付金额；已退款表示商家手动确认已在 App 外退回整单金额 |
| 履约状态 | 待履约 / 已发货 / 已交付 | 配送订单使用已发货，自取订单使用已交付；两者不同时出现 |

草稿的付款和履约维度尚不适用，不能在草稿上登记付款或发货。“已分享”不是付款状态，“已发货”不是已收款证明，订单状态也不使用“已付款”代替。

首版不额外增加可手动切换的“已完成”订单状态。有效订单在“已付款 + 已发货 / 已交付”后归入历史；该分组只表示商家流程已结束，不表示配送已签收。

### 6.2 状态变化与约束

| 操作 | 前提 | 结果与限制 |
| --- | --- | --- |
| 正式保存 | 草稿通过金额与字段校验，且有创建额度或 Pro 权益 | 已建立 + 未付款 + 待履约；首次成功保存占用一次新订单额度 |
| 标记已付款 | 已建立 + 未付款 + 待履约；商家确认真实到账 | 付款变为已付款，记录登记时间；分享、导出和二维码被扫描均不能触发此变化 |
| 纠正误标付款 | 已建立 + 已付款 + 待履约，且从未登记履约或退款；确属误标 | 单独确认并填写原因后改回未付款，保留纠正记录；不能用此操作代替真实退款，金额仍保持锁定 |
| 登记发货 / 交付 | 已建立 + 已付款 + 待履约 | 按配送 / 自取变为已发货 / 已交付；首版不支持未收款先发货或反向切换履约状态 |
| 取消订单 | 已建立 + 待履约，且付款为未付款或已退款 | 主状态变为已取消；保留原金额、付款记录和取消时间，不能重新启用或发货 |
| 登记整单退款 | 已建立 + 已付款；商家已在 App 外实际完成退款 | 付款变为已退款，记录退款金额、登记时间和说明；不自动撤销原发货 / 交付事实 |

- 已付款且未履约的订单，必须先在 App 外退款并登记“已退款”，再取消。不能直接取消并让已收款事实消失。
- 已发货 / 已交付的订单不能取消。可以登记整单退款，保留“已建立 + 已退款 + 原履约状态”，作为已结束的退款历史。
- 已退款订单不能再标记已付款、生成付款通知或登记发货。后续新交易应新建订单；首版不支持部分退款、撤销退款或商品退回管理。
- 已取消订单只读，不能标记已付款、发货或恢复。取消后的外部收款异常需由商家在 App 外核实处理，App 不自动核账。
- 同一次状态操作应完整保存；失败时保留操作前状态，不能出现已显示成功但记录未保存的情况。

### 6.3 编辑权限与金额锁定

| 订单条件 | 允许编辑 | 不允许编辑 |
| --- | --- | --- |
| 草稿 | 所有订单输入字段 | 不允许登记付款、退款或履约 |
| 已建立、未付款、待履约，且从未登记付款或履约 | 商品、数量、价格、折扣、运费、客户及履约信息；显式更新收款资料和模板 | 订单唯一标识、创建时间 |
| 曾登记付款或履约，当前未取消 / 未退款 | 内部备注；按上表执行允许的状态操作 | 商品、数量、单价、折扣、运费及总额；已确认的对外资料和快照 |
| 已退款、尚未取消 | 查看、搜索、导出备份；仅待履约时允许取消订单 | 改金额、改商品、覆盖客户或收款快照、撤销退款或继续履约 |
| 已取消 | 查看、搜索、导出备份 | 改金额、改商品、覆盖客户或收款快照、反向修改终止状态 |

曾登记付款或履约即持续锁定金额，纠正误标也不会重新解锁。发现锁定订单金额错误时，依实际资金和履约情况处理原单，再新建正确订单，不能直接覆盖历史金额。这里的内部备注与发送给客户的订单备注分开，内部备注不进入 PNG。

## 7. 金额计算与历史快照

### 7.1 计算规则

数据层统一使用整数分保存和计算金额；界面按 HKD 显示两位小数。不能用浮点数计算后仅靠显示层四舍五入掩盖误差。

| 项目 | 规则 |
| --- | --- |
| 商品行金额 | 单价（整数分）× 数量（正整数） |
| 商品小计 | 所有商品行金额之和 |
| 折扣 | 整单固定金额，必须 ≥ 0 且 ≤ 商品小计；仅扣商品金额，不抵扣运费 |
| 运费 | 必须 ≥ 0；自取默认 0；切换为自取时明确提示并清零运费 |
| 应付总额 | 商品小计 − 折扣 + 运费，正式订单必须 > 0 |
| 单价输入 | 允许 0，但订单最终总额须 > 0；最多两位小数，额外精度提示修正，不静默截断 |
| 不合法金额 | 负数、非数字、超出支持范围的值不得保存；支持的金额上限须在开发前验证并于发布前冻结 |

核对示例：HK$88.50 × 2，加 HK$39.90 × 1，商品小计为 HK$216.90；折扣 HK$16.90、运费 HK$30.00，应付总额为 **HK$230.00**。对应整数分计算为 21,690 − 1,690 + 3,000 = 23,000。

首版不另加税费、手续费、汇率或隐藏费用。编辑页、订单列表、PNG 和备份恢复后的金额必须一致。

### 7.2 历史订单快照规则

- 正式保存时保留该订单的商品名称、数量、单价、折扣、运费、总额、客户与履约信息、店铺名称、Logo、收款说明、选定二维码和图片语言 / 模板选择。
- 商品价格变更不影响历史订单。首版商品为逐单手填；以后即使增加商品资料，也不得通过商品现价回算旧单。
- 店铺改名、更换 Logo、替换收款二维码或切换界面语言，不自动回写已有订单。
- 尚未付款且从未登记付款 / 履约的有效订单，可由商家明确选择更新订单或收款资料；更新后旧预览失效，必须重新生成，提示已发送的旧图不会自动更新。
- 金额锁定、取消或退款后保留原快照。不能用当前配置填补旧订单缺失的收款图片并假装它一直属于旧单。
- 源相册图片被删除不应导致已保存资料丢失；若 App 本地副本确实缺失，则按异常规则提示，不得静默分享缺失内容。

## 8. 取消、退款与历史订单

### 8.1 取消与记录保留

取消仅允许“待履约，且付款为未付款或已全额退款”的有效订单。取消前展示订单编号、金额和当前付款状态，并说明保留历史且不能恢复；可记录取消原因。

取消不删除记录、不清空金额、不返还 Free 已使用的新订单额度，也不自动修改真实资金情况。已付款且未退款时阻止取消，并解释先完成外部退款与登记的要求。

### 8.2 首版退款边界

只支持**手动登记整单退款**，退款金额固定等于原订单应付总额，包含已计入总额的运费。商家实际只退部分金额时不能谎报为整单退款，首版不承接该业务流程。

登记前必须明确提示“请先确认已在收款渠道完成退款”，并二次确认金额。OrderMori 不发起退款、不连接银行或支付工具，也不把“登记已退款”描述为退款已经由 App 执行。

### 8.3 历史展示

以下任一条件成立即归入历史：已取消；已退款；或已付款且已发货 / 已交付。已退款且待履约的订单也属于历史，不能继续履约；仍可按第 6 节取消。

历史保留原商品、金额、订单编号、创建时间、当前三维状态，以及已登记的付款、退款、取消和履约时间。退款订单同时展示原应付金额和整单退款金额，不将原总额改成 0。状态纠正记录只需在订单详情可查，不建立复杂审计或财务报表。

## 9. PNG、二维码与分享边界

### 9.1 付款通知内容与排版

- PNG 使用纵向排版，优先适合手机阅读，内容按实际长度展开。宽度暂定 1080 px，最终尺寸与最长订单边界需通过真机分享验证，不能用无限长图片规避可读性和内存限制。
- 展示店铺名、可选 Logo、订单编号 / 日期、商品与数量、单价与行金额、商品小计、折扣、运费、突出显示的应付总额、收款方式与必要说明；可选客户称呼和对外备注。
- 私人联系方式、配送地址和内部备注不默认输出到付款 PNG。首版不增加地址排版或地址公开开关。
- 商品名和备注按行展开，不用省略号隐藏应付款项，也不缩小到无法阅读；总额、二维码及其说明不可截断。
- 图片内有明确标题“付款通知 / Payment Note”，以及“仅供付款通知，并非正式收据或已收款确认”的对应语言说明。不得显示暗示资金已到账的收据措辞或标记。
- 图片语言首次按当前界面语言确定，保存在订单中；之后切换 App 语言不会静默改写旧图。

### 9.2 二维码来源与展示

- **不自行生成未经验证的 PayMe / FPS 收款二维码**，不拼接付款码内容，不声称可自动把订单金额写入官方收款码。
- 二维码由商家从官方支付工具或官方渠道取得并上传。商家负责确认收款对象正确；App 仅保存和展示，不声称验证收款账户或实际到账。
- 保留原图比例、清晰度和二维码周围必要留白，不染色、不反转、不拉伸、不覆盖 Logo、不套装饰滤镜；两款模板遵守相同规则。
- 正式验收须使用商家授权的测试二维码，经实际生成、分享和接收后扫码验证。涉及转账时由测试人员自行核实，不执行真实付款作为自动化验证。
- 二维码不可读或丢失时，不生成依赖该二维码的付款通知。商家可为仍可编辑的未付款订单补选有效官方图片，或明确改选已经配置的文字收款方式。

### 9.3 分享边界

分享通过 iOS 系统分享面板，用户自行选择 App 和联系人。OrderMori 不承诺自动发送到指定联系人、不控制聊天工具压缩、不获取客户是否已查看，也不将分享面板返回成功等同于送达。

用户取消分享时订单保持原状；分享失败允许重试，不重复创建订单或消耗新订单额度。没有网络时可生成图片并打开系统面板，实际外部发送是否成功由接收 App 决定。无论分享、保存图片还是扫码，付款状态均不自动变为已付款。

## 10. Free / Pro 方案

以下分配为 **v1.0 暂定商业策略，待真实用户与购买流程验证**；发布前应在本文确认最终额度和权益。

| 权益 | Free（暂定） | Pro（暂定） |
| --- | --- | --- |
| 新订单额度 | 每个设备本地自然月最多新建 30 笔正式订单 | 不设置商业数量上限，仍受设备容量和产品输入边界限制 |
| 模板 | 韩系柔和 | 韩系柔和 + 黑白极简 |
| 图片产品署名 | 显示轻量 OrderMori 署名，不遮挡内容和二维码 | 可移除 OrderMori 产品署名；付款通知说明仍保留 |
| 已有订单管理、状态登记 | 可用 | 可用 |
| 订单查看、历史搜索 | 可用 | 可用 |
| 本地备份与恢复 | 可用 | 可用 |
| 已有可分享订单的重复生成与分享 | 不按分享次数收费 | 同左 |

### 10.1 免费额度规则

- 仅从草稿第一次成功保存为正式订单时计数；编辑、重试保存、标记状态、重新生成图片或重复分享不重复计数。
- 删除草稿不计数；取消或退款不返还已用额度。首页显示剩余额度和依本机日历计算的重置日期。
- 额度用尽后阻止新建正式订单，保留当前草稿并提供升级说明；仍可查看和管理已有订单、登记真实付款 / 履约 / 退款、备份和恢复，不扣留用户数据。
- 备份包含必要的本地额度记录；恢复同一备份不重复计数，也不以恢复为理由重发额度。本机与备份记录按订单标识去重，同月已用额度不因恢复旧文件回退。
- 首版不做跨设备额度核算或可靠防篡改承诺；设备时间、重装与迁移场景的局限需要在发布前验证。

### 10.2 买断与权益行为

Pro 采用一次性买断方向，首版不做订阅。具体价格、地区价格和是否采用首发优惠均待验证，本文不写死最终售价；购买界面显示平台实际可购买的本地化价格。

已确认有效的本机 Pro 权益支持离线使用。首次购买或在新设备恢复购买需要网络和平台服务；失败、待处理或无法确认时不虚假解锁，也不因短暂离线抹去最后已确认有效的权益。明确收到权益失效结果后回到 Free，但保留所有订单和备份能力。

恢复数据与恢复购买是两个独立操作：备份内的“曾是 Pro”信息不授予购买权益。恢复购买无匹配记录、网络失败或平台异常时，说明原因并提供重试。客户订单退款与 Pro 买断购买退款是不同事项，不共用业务状态。

当现有订单超过 Free 额度或使用了 Pro 模板时，降为 Free 或导入备份都不删除记录；不能创建超额新单。超出当前模板权益的未付款订单仍可查看原预览；仍允许编辑模板的订单可明确改选 Free 模板后重新生成 / 分享，也可恢复 Pro。锁定快照不能以权益变化为由改写，其他生成 / 分享条件仍按第 5、6 节执行。

## 11. 本地备份与恢复

- 备份由用户主动导出为文件，包含草稿、正式及历史订单、状态和必要变更记录、历史快照、店铺设置、Logo、收款二维码及本地额度记录；不能只导出失效的图片路径。
- 导出只保存一份可恢复的本机资料副本，不包含支付登录凭证或可直接授予 Pro 的权益。明确提示备份含客户及收款资料，应由用户妥善保管。
- 用户可通过系统文件选择或分享保存到自己选择的位置；这不构成 App 的自动云同步。不配置自动上传、服务器备份或跨设备后台任务。
- 首版只支持整体替换恢复，不做合并订单。恢复前校验文件格式、备份版本、数据完整性与必要图片，展示备份时间和订单数量，提示将替换当前业务数据，并建议先导出当前数据。
- 整体替换仅针对备份涵盖的业务资料；已确认的本机购买权益不被备份覆盖，本机同月已用额度按第 10 节保留。恢复本身不重复消耗额度。
- 确认后恢复全部成功才切换为恢复结果；校验或写入失败保留原业务数据。损坏、版本不支持或图片不完整的备份拒绝恢复，不做无提示的部分导入。
- 恢复超出免费额度的备份时允许恢复全部记录并提示限制，不能以升级为前提扣住历史。换设备恢复业务数据后，Pro 仍需通过恢复购买确认。

## 12. UI / UX Design Principles

### 12.1 整体视觉目标

OrderMori 应让用户感到**清爽、精致、专业、有品质感**。面向小商家不意味着廉价；界面应比普通工具 App 更好看，且足够舒适，让用户愿意长期停留和重复使用。

美观必须服务任务：金额准确、状态可辨、分享有信心，比堆砌装饰更重要。通过少数界面中稳定的字体、间距、细节和反馈建立品牌，而非靠大面积装饰吸引注意。

### 12.2 设计风格方向

- 现代、简洁、轻盈，偏 iOS 原生审美；优先沿用用户熟悉的返回、表单、选图和系统分享方式。
- 使用适度品牌色和克制的装饰，不花哨；品牌识别集中在细节和付款模板中。
- 使用卡片式信息分组，但不把每一行都套成独立卡片；每屏有清楚的标题、主要内容和主要操作。
- 重视留白、字体层级、行距、对齐、圆角和轻量阴影。阴影用于说明层级，不造成厚重后台感。
- 金额采用易比较的数字排版，HKD 币种与小数位清楚；正文和金额字体以阅读为先，不使用影响识别的装饰字。
- 页面不应有明显的“开发者工具感”或“管理后台感”：避免拥挤数据表、密集按钮、实现术语和调试信息。

### 12.3 关键体验要求

| 页面 / 场景 | 必须达到的体验 |
| --- | --- |
| 新建订单 | 顺手、少重复输入；合理默认数量、合适键盘、就近校验；增加商品不中断节奏，返回不丢输入 |
| 首页列表 | 编号 / 客户、总额、当前待办一眼可见；标签克制，避免每张卡片塞满明细；空状态有明确下一步 |
| 付款图片预览 | 看起来值得分享；预览忠实于导出，不以低清缩略图掩盖裁切；二维码与金额可放大核对 |
| 店铺设置 | 首次必填与可选内容分组，解释为什么要上传收款码；基础配置目标暂定不超过约 3 分钟，不包含寻找官方二维码的时间 |
| 金额与状态 | 总额突出且易读；付款和履约分别标记，文字与颜色共同表达；标签清晰但不过于刺眼 |
| 保存、生成、分享 | 主操作名称直接表达结果；保存成功、处理中、失败、取消各有准确反馈；不能把“生成”反馈成“已发送” |
| 错误与限制 | 指出问题和可执行的修复方法，保留输入；升级提示不阻断历史和备份 |

### 12.4 首版两个模板

| 模板 | 视觉方向 | 共同质量要求 |
| --- | --- | --- |
| 韩系柔和 | 暖白或低饱和柔和底色、精致间距、轻盈分组，呈现亲切但专业的小店气质 | 美观、易读、品牌感强，适合商家发送给客户；金额和二维码不因装饰失去对比 |
| 黑白极简 | 清晰黑白对比、克制线条、整齐对齐和干净留白，强调专业与可信 | 与柔和模板拥有相同信息完整性；不是把同一模板简单去色 |

两款模板均需在最长支持商品名、最多商品行、长备注、可选 Logo 缺失及中英文内容下验证。二维码保留清楚白底和必要留白；长商品名换行后，价格、总额及扫码区域仍有稳定位置，不能出现覆盖、挤出或裁切。

### 12.5 可读性、可访问性与反馈

- 核心内容和操作在最小支持 iPhone 屏幕、大字号及键盘打开时仍可阅读和触达；支持的设备与系统范围在开发前确认。
- App 正文随系统字号调整，不能因大字号隐藏金额或按钮；交互触控区域目标不小于 44 × 44 pt，不把静态 PNG 的字号适配与界面适配混为一谈。
- 普通正文与背景的对比度目标至少 4.5:1；状态不能只依赖颜色，配合文字。主要按钮、输入和状态标签使用一致的视觉规则。
- 关键表单、金额、状态和操作提供有意义的辅助阅读标签，VoiceOver 阅读顺序符合业务顺序；错误提示能被发现。
- 动效简短、可减少，用于解释状态和操作反馈；不以开场动画、过度弹窗或装饰动画打断高频开单。
- English 和繁體中文（香港）分别检查文字长度、换行及常用说法。界面文案面向商家，不暴露文件路径、字段名或内部错误堆栈。

### 12.6 后续设计原则

后续开发不为赶工牺牲核心界面质量。先把少数页面做精，再决定是否增加功能；交互与视觉质量本身是产品竞争力的一部分。遇到时间冲突时优先缩减非核心范围，不以粗糙首页、难用开单或不好看的付款图片作为完成标准。

本节定义产品质量方向，不在 PRD 中固定完整颜色令牌、组件库、线框稿或页面代码。视觉细化仍必须遵守本 PRD 的业务和状态边界。

## 13. 异常场景与预期处理

| 场景 | 预期处理 |
| --- | --- |
| 未设置收款方式 / 店铺名称 | 可保留订单和草稿；生成付款通知前定位到缺失设置，不显示虚构账户 |
| 二维码丢失、损坏或过于模糊 | 阻止依赖该码的生成和分享；保留订单；可编辑未付款订单允许补选官方图或明确改选已有有效文字方式；锁定历史只可通过完整备份恢复原图 |
| 本地 Logo / 预览图片文件丢失 | Logo 缺失时说明并由用户确认是否在可编辑订单中移除；缺预览可从完整快照重生成；不能用当前店铺图片静默覆盖锁定历史 |
| 商品名过长或超过商品行上限 | 输入时展示边界；范围内正常换行，超限说明后阻止保存，不静默截字或导出半张图片 |
| 总额为 0、负数或折扣超限 | 显示费用拆分和具体问题，阻止正式保存 / 生成，保留草稿 |
| 输入含无效精度或超出金额支持范围 | 定位对应字段，要求修正；不能四舍五入后偷偷改变商家输入 |
| 生成 / 分享失败、用户取消分享 | 允许重试或返回；不重复创建订单、不增加额度、不改付款状态，不声称客户已收到 |
| 离线分享、购买或恢复购买 | 可离线生成和打开分享面板；说明外部发送及购买服务可能需要网络；保留最后已确认权益和当前输入 |
| 未购买 Pro 且超出免费额度 | 阻止新的正式订单保存，保留草稿，解释额度和升级；已有订单、状态管理和备份可继续 |
| 购买取消 / 待处理 / 失败 | 分别提示当前结果，不错误激活、不自动反复购买，保留原操作上下文 |
| 恢复购买失败或无匹配记录 | 给出可理解的原因及重试入口，不授予未知权益，也不删除订单 |
| 备份损坏、版本不兼容或图片不全 | 恢复前拒绝并解释；不部分覆盖当前数据，允许重新选择文件 |
| 备份导出中断或磁盘空间不足 | 保留本机数据，不把半成品描述为成功备份，说明清理空间或重试 |
| 试图取消已付款未退款 / 已发货订单 | 根据状态说明先退款登记或只能保留履约历史，不能直接取消 |
| 试图修改已付款、已退款、已取消订单金额 | 清楚显示锁定原因和允许的后续操作，不提供绕过状态的金额编辑 |
| 恢复超量或曾使用 Pro 模板的备份 | 全部保留并可查看；新建和重新生成遵守当前真实权益，不从备份自动解锁 Pro |

## 14. 发布验收标准

以下为后续实现的发布门槛，本次文档提交不代表这些测试已经执行或通过。必须在确认的支持设备上使用脱敏样例及商家授权的测试收款图进行验收。

| 编号 | 验收项目 | 通过条件 |
| --- | --- | --- |
| AC-01 | 离线可用 | 飞行模式下可新建、保存、编辑允许编辑的订单、查看历史、登记允许的状态、改设置、生成 PNG，并在本地文件可访问时导出 / 恢复备份；购买联网例外明确 |
| AC-02 | 数据持久化 | 保存成功后强制关闭并重启 App，订单、草稿、状态、设置、快照图片及最后已确认权益不丢失；写入失败不反馈成功 |
| AC-03 | 金额准确 | 第 7 节示例得到 HK$230.00；覆盖两位小数、折扣边界、数量边界、0 总额和超限输入；列表、编辑、PNG、备份恢复结果一致，无浮点误差 |
| AC-04 | 状态约束 | 三维状态独立；仅允许第 6 节列出的变化；已付款 / 曾付款锁金额，已发货不能取消，退款保留履约事实，终止状态不能反向修改 |
| AC-05 | 不错误确认收款 | 生成、保存或分享图片、取消分享、分享面板完成、扫码均不标记已付款；只有商家明确确认到账操作可登记付款 |
| AC-06 | 图片不截断 | 两款模板在中英文、120 字符商品名、20 项商品和 500 字符备注的暂定边界下完整显示；若边界调整则同步验收用例；总额、说明和二维码不重叠、不裁切、不缩成难读字号 |
| AC-07 | 二维码可扫 | 对授权官方来源图片，从 App 生成、经目标聊天工具手动分享并由另一设备接收后仍可被对应支付工具识别；收款对象与原码一致；失败先修复导出 / 排版，不自行重编码 |
| AC-08 | 分享后清晰 | 在计划支持的代表性分享路径中检查接收图片：商品、费用拆分和总额清楚，二维码可扫，付款通知说明保留；不能只检查 App 内预览。首要验证路径暂定为 WhatsApp 手动分享，其他路径以实际测试范围为准 |
| AC-09 | 历史快照 | 修改店铺、Logo、二维码和新订单价格后旧订单不变；退款不把原总额改为 0；删除源相册图不破坏已经保存的本地副本 |
| AC-10 | 备份恢复成功 | 含草稿、未付款、已付款、已发货、取消及退款订单和两种模板资料的备份整体恢复后，逐项金额、状态、历史时间和图片一致；重复恢复不产生重复订单或额外额度 |
| AC-11 | 恢复失败安全 | 损坏、版本不支持、图片缺失及写入失败时原数据完整保留；未确认替换前不修改业务数据；备份不授予 Pro |
| AC-12 | Free / Pro 行为正确 | 验证第 30 / 31 笔暂定边界、跨月重置、重复保存 / 分享、取消不返额、超量备份、权益失效、模板限制；Free 仍可管理历史和备份 |
| AC-13 | 购买结果准确 | 后续在平台测试环境验证成功、取消、待处理、失败及恢复购买；仅确认有效后解锁，离线不抹去已确认权益，失败不丢当前订单 |
| AC-14 | 核心 UI 质量 | 最小支持屏幕、大字号和键盘场景无关键内容遮挡；状态标签、主要操作和错误提示清楚；VoiceOver 可完成核心路径；两款模板分别完成视觉与扫码检查 |
| AC-15 | 易用性 | 暂定用 5 名代表性商家验证：至少 4 名在基础配置后无需讲解完成一张 3 项商品订单并找到正确分享入口；记录约 60 秒目标的实际表现；不以增加隐藏快捷键替代流程修正 |
| AC-16 | 本地边界 | 没有未声明的订单 / 收款图自动上传，没有云同步或聊天自动投递；用户可理解数据只在本机及自己导出的备份中 |

发布前应记录实际设备、系统、语言、样例及分享路径。若核心金额、持久化、状态安全、图片完整性、扫码或备份验收失败，不应以其他功能数量补偿通过。
